GenAI Application Patterns on AWS

Good news: a GenAI app is ~90% ordinary AWS architecture. This chapter gives you the reference architecture, the six integration patterns that cover almost every use case, and the resilience playbook for the other 10%.

8.1 · The big picture

The reference architecture you'll keep reusing

Strip away the AI mystique and a production GenAI app looks like every serverless app you've seen — with Bedrock as one more downstream dependency, plus three AI-specific attachments: a knowledge base, a guardrail, and conversation state.

Familiar bones: authentication, throttling, and validation live exactly where they always did. Only the orange box is new — and you already know it from Chapter 2.

Migration lens: this is the same 3-tier shape as the on-prem app you just moved — load balancer → app server → backend — with the "backend" being a reasoning engine instead of (or alongside) a database. Your instincts about timeouts, pooling, and bulkheads all transfer.

8.4 · State & memory

Models are stateless. Your app isn't.

From Chapter 2: the model forgets everything between calls. "Memory" is an application feature you build — and it's plain data engineering:

🗂️ Conversation history

Store messages in DynamoDB keyed by session_id; replay the recent window (or a running summary) into each Converse call. TTL attribute = automatic retention policy.

Watch out: resending the full history every turn is your #1 hidden token cost.

⚡ Response caching

Identical FAQ-style questions shouldn't hit the model twice. Hash the normalized prompt → check ElastiCache → serve in milliseconds for ~zero cost.

Level up: semantic caching (match by embedding similarity) — Chapter 10.

🧠 Long-term memory

User preferences and facts extracted across sessions ("prefers Terraform examples"). Store per-user; inject as context. AgentCore Memory manages this for agents.

Governance: this is PII — retention and access rules apply (Ch. 6/9).
8.5 · When it breaks

The resilience playbook for a probabilistic dependency

Bedrock brings two twists to your standard playbook: throttling is normal (token throughput is quota-bound) and bad responses aren't exceptions (the call succeeds; the content is wrong). Handle both:

# The four layers of a resilient model call
def robust_invoke(msgs, attempt=0):
    try:
        resp = bedrock.converse(modelId=PRIMARY, messages=msgs,
                                guardrailConfig=GR, inferenceConfig=CFG)
        out = parse_and_validate(resp)          # 1. schema-validate the CONTENT
        return out
    except ThrottlingException:
        if attempt < 3:
            sleep(2 ** attempt + jitter())       # 2. backoff+jitter — throttling is normal
            return robust_invoke(msgs, attempt + 1)
        return converse_with(FALLBACK, msgs)     # 3. fallback model / cross-region profile
    except ValidationFailure:
        return retry_with_repair_prompt(msgs)    # 4. "your last output was invalid JSON…"

⏱️ Timeouts that fit LLMs

A long completion can take 30–90s. Set client timeouts accordingly, stream when a human waits, and go async (SQS) past ~30s.

🔀 Fallback chains

Primary model → cross-region inference profile → smaller fallback model → cached/static response. Degrade gracefully, never to a spinner.

🚦 Quota awareness

Bedrock quotas are per model/region in tokens-per-minute. Track usage in CloudWatch, alarm at 70%, and request increases before launch day.

8.6 · Ship it properly

Everything is infrastructure — including the AI parts

Guardrails, knowledge bases, prompts, agents: all first-class resources in CloudFormation and CDK. If it's clicked together in the console, it can't be code-reviewed, promoted through environments, or rolled back.

# CDK: the AI resources deploy like any other (TypeScript)
const guardrail = new bedrock.CfnGuardrail(this, "CorpGuardrail", {
  name: "corp-assistant",
  contentPolicyConfig: { filtersConfig: [{ type: "VIOLENCE", inputStrength: "MEDIUM",
                                           outputStrength: "MEDIUM" }] },
});

const chatFn = new lambda.Function(this, "ChatFn", { /* … */ });
chatFn.addToRolePolicy(new iam.PolicyStatement({
  actions: ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream"],
  resources: [novaLiteArn],                    // least privilege: ONE model, not "*"
}));
Pipeline shape: same CI/CD you built for the migrated apps — plus two GenAI stages: run the golden prompt test set (Chapter 3) against the new build, and smoke-test guardrails with known-bad inputs (Chapter 6). Promotion to prod is blocked on both, exactly like unit tests.
8.7 · Field guide

Architecture failures → quick fixes

Synchronous API Gateway call for a 2-minute document analysis
SQS + worker + status endpoint (or WebSocket push) — respect the 29s gateway timeout
Calling Bedrock straight from the browser with embedded credentials
Always through your backend: auth, guardrails, logging, and cost control live there
One Lambda doing retrieval + prompting + validation + notification
Step Functions with small single-purpose steps — retryable, observable, testable
Ignoring streaming because "the API works without it"
Stream any human-facing response >2s — perceived latency is the UX
Batch-processing 100k documents through the on-demand API in a loop
Bedrock batch inference: ~half the cost, no throttling fight
Hardcoded model IDs scattered through the codebase
Model ID + parameters in AppConfig/SSM — swap models without a deploy (Ch. 2)

🧪 Hands-on lab (~90 min)

1. Build the reference architecture: API Gateway → Lambda → Bedrock Converse, with conversation history in DynamoDB and your Chapter 6 guardrail attached. (CDK or console — but try CDK.)

2. Add the async pattern: an S3 upload triggers a Lambda that summarizes the document and writes the result back — your first event-driven enrichment.

3. Break it on purpose: set a 3s Lambda timeout and watch the failure mode; then fix it with streaming or the queue pattern.

🎯 Chapter 8 takeaways

  1. A GenAI app is 90% ordinary AWS architecture — Bedrock is one more downstream dependency with a knowledge base, guardrail, and state attached.
  2. Pick patterns by asking: is a human waiting, and for how long? Sync → streaming → async → batch, plus event-driven and Step Functions orchestration.
  3. Memory is your job: DynamoDB history (mind the token cost), caching for repeat questions, per-user long-term memory with PII governance.
  4. Two resilience twists: throttling is normal (backoff + fallback chains + quota alarms) and bad content isn't an exception (validate every response, retry with repair prompts).
  5. AI resources are infrastructure as code — guardrails, KBs, prompts in CDK, with golden-prompt tests gating promotion.
  6. Never call Bedrock from the client; stream anything a human watches; batch anything they don't.
