Cost Optimization & Performance: Token Economics

GenAI bills differently from anything in your data center: not per server, per hour, or per GB — per word. Master the token economy and the latency levers, and your AI features stay fast and affordable at scale.

10.1 · The bill, demystified

Three things the sliders teach: ① output tokens cost ~4–5× input tokens — cap them; ② the model tier is a ~60× swing — right-size before anything else; ③ that "input tokens" slider is mostly your own context and history (Ch. 8's hidden cost) — trim what you resend.

10.3 · The router pattern

Model cascading: cheap first, escalate when needed

Most traffic is easy. A router sends every request to a small model first; only requests it can't handle confidently escalate to the frontier tier. Watch: teal = simple queries (~80%), pink = the hard one that escalates.

Bedrock's Intelligent Prompt Routing does this as a managed feature within a model family; build your own router when you need custom rules (Ch. 8's AppConfig-driven model selection).

10.4 · Free money

Three caches, three layers

1 · Exact-match cache

Hash the normalized prompt; store the response with a TTL. Trivial to build (Ch. 8), perfect for FAQ-shaped traffic.

Catch: "reset VPN?" vs "how do I reset the VPN?" are different keys — misses meaning.

2 · Semantic cache

Embed the question (Ch. 4!) and match by similarity above a threshold — those two VPN questions now hit the same entry.

Catch: tune the threshold carefully; a wrong-but-similar answer is worse than a miss.

3 · Bedrock prompt caching

A managed feature: mark the static prefix of your prompt (system prompt, few-shot examples, big document) as a cache checkpoint — repeated prefixes are reprocessed at a fraction of the cost and faster.

Best for: long shared context asked many questions — "chat with this contract."
10.5 · Performance

Latency: manage the wait, then shrink it

Two numbers rule GenAI latency: time to first token (TTFT — when the user sees life) and tokens per second (how fast it finishes). The same 500-token answer, three ways — the white tick marks TTFT:

🏎️ Latency-optimized inference

Some Bedrock models offer a latency-optimized tier — one request flag for meaningfully faster tokens, at a premium. Reserve it for the interactions where speed is the feature.

🧵 Parallelize the independent

Summarizing 5 documents? Five concurrent calls, not a loop. Watch quota headroom (Ch. 8) — parallelism spends tokens-per-minute faster.

📏 Shorter output = faster output

Generation time scales with output length. The output cap from lever #3 is also your best latency lever — cost and speed improve together.

10.6 · You can't optimize blind

Cost visibility: know who spends what

On-demand Bedrock usage lands in Cost Explorer per model — but not per application, unless you set that up:

# Application inference profile: tag a model per app for cost allocation
aws bedrock create-inference-profile \
  --inference-profile-name claims-app-nova-lite \
  --model-source copyFrom=arn:aws:bedrock:us-east-1::foundation-model/amazon.nova-lite-v1:0 \
  --tags key=app,value=claims key=cost-center,value=ops-migration

# Apps invoke via THEIR profile ARN → spend shows up per app/cost-center

10.7 · Field guide

Cost & performance failures → quick fixes

Frontier model for everything "because quality"
Golden test set on the small tier first — route up only what fails (10.3)
Replaying the full conversation history every turn
Sliding window + running summary; history is your biggest silent input-token bill
No maxTokens set — "the model knows when to stop"
Cap per use case; output tokens are the expensive, slow direction
Buying provisioned throughput at launch "to be safe"
Launch on-demand, measure 4–6 weeks, then commit to the observed baseline
One shared account/profile — monthly bill is a mystery blob
Application inference profiles + tags → per-app spend in Cost Explorer (10.6)
Chasing p50 latency while p95 users suffer
Alarm on p95 TTFT; stream everything human-facing — perceived speed is the metric

🧪 Hands-on lab (~60 min)

1. Rebuild your Chapter 8 app's cost model in the section 10.1 calculator with real numbers from your invocation logs (Ch. 9) — then check the actuals in Cost Explorer.

2. Run your Chapter 3 golden test set against a model one tier smaller — record the pass rate and the cost delta. That's lever #1, quantified.

3. Add an exact-match cache (DynamoDB, hashed prompt key, TTL) in front of your app and measure the hit rate after a day of use.

4. Create an application inference profile with cost-allocation tags and switch your app to it.

5. Deeper: Bedrock pricing · prompt caching docs · GenAI Lens: cost pillar.

🎯 Chapter 10 takeaways

  1. The bill is tokens × rate, and output tokens cost ~4–5× input — cap and shape output first.
  2. Pull levers in order: right-size the model (10–60×), trim context, cap output, cache, batch, then provisioned throughput last.
  3. Model cascading routes ~80% of traffic to cheap models and escalates the rest — blended cost near the small tier, quality near the large one.
  4. Three cache layers: exact-match, semantic, and Bedrock prompt caching for long shared context.
  5. Latency = TTFT + tokens/sec: stream for perceived speed, right-size and cap for real speed, parallelize independent calls.
  6. Visibility before optimization: application inference profiles + tags for per-app spend, budgets and anomaly alarms, and unit economics the business understands.
