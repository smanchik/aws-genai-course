AWS Generative AI · Chapter 13 · Capstone II

AIOps: Automated Incident Troubleshooting for a Tier-1 Application

Chapter 12 used GenAI to serve customers. This capstone points it at your own operations: an incident-response agent that reads the logs, correlates the transactions, remembers every past resolution — and cuts your 2 a.m. MTTR from hours to minutes.

13.1 · The scenario

The patient: HealthFirst Member Portal (Tier-1, already on AWS)

A customer-facing health-plan portal where members check plan information, medical claims, benefits, and network providers. It's already migrated and running on AWS — this project doesn't touch the portal itself. It builds the brain that operates it. Your raw materials:

🧾

Transactions

Every API call the portal makes — claims lookups, eligibility checks, provider searches — with status, latency, and correlation IDs (API Gateway/ALB access logs, X-Ray traces).

🖱️

User interactions

Clickstream of member journeys: pages visited, errors shown, abandoned flows (CloudWatch RUM / Kinesis → S3, queryable via Athena).

🪵

Debug & error logs

Application logs across services in CloudWatch Logs — stack traces, timeouts, dependency failures — searchable with Logs Insights.

🚨

Incident system

ServiceNow/Jira/PagerDuty incidents from monitoring alarms and member complaints — plus years of resolution notes and postmortems nobody re-reads.

The objective: when an incident arrives, the system automatically ① analyzes the relevant logs and transactions, ② recalls how similar incidents were resolved before, ③ proposes (or safely executes) a remediation, and ④ writes back an enriched incident — so the on-call human starts at step 8, not step 1.
13.2 · Target architecture

One agent, four tool families, one knowledge loop

Watch the flow: an incident (red) triggers the agent; the agent fans out to its evidence tools (cyan) — logs, transactions, clickstream, past resolutions; a remediation (teal) goes out only through the approval gate.

Every arrow is a Chapter 5 tool with a typed schema. Evidence tools are read-only by IAM; only the bottom path can change anything — and it passes a human first.

Where each chapter shows up: the agent loop and tools (Ch. 5) · the resolution KB is managed RAG (Ch. 4) · PHI masking guardrails (Ch. 6) · EventBridge intake is the event-driven pattern (Ch. 8 #4) · read-only IAM and audit logging (Ch. 9) · a small router model triages severity cheaply before the big model reasons (Ch. 10) · agent traces feed evaluation (Ch. 11).

13.4 · The compounding asset

The knowledge loop: every incident makes the next one faster

The Knowledge Base of past resolutions is what separates this from a fancy log searcher. Close the loop and it compounds:

The postmortem nobody re-reads becomes the first thing the agent reads. Six months in, your KB knows more about this system's failure modes than any single engineer.

Seeding tip: don't wait for new incidents. Batch-ingest (Ch. 10) your existing postmortems, closed-ticket resolution notes, and runbooks on day one — even messy ones. Chunk hierarchically (Ch. 4) so "symptom" and "fix" stay together, and tag by service for metadata filtering.
13.5 · Non-negotiables

PHI, permissions, and the pager: safety for a health-plan portal

This is healthcare data and a Tier-1 system — the controls are the design, not decoration:

🩺 PHI never reaches the model raw

Logs and transactions can contain member IDs, names, and claim details. A masking layer (Comprehend PII / guardrail PII policy, Ch. 6) scrubs tool outputs before they enter the prompt — the agent reasons over {MEMBER_ID} tokens, not identities.

Verify: run Macie over the log buckets; test with seeded fake PHI.

🔐 Read-only until proven

Evidence tools get read-only IAM roles (Ch. 9). Remediation tools exist in a separate, tightly-scoped role — and each runbook lists exactly which SSM documents it may execute.

Start: weeks 1–8 the agent only recommends. Autonomy is earned with a track record.

🙋 Approval for anything that touches prod

Restart, rollback, scale-out — every write action pauses for on-call approval in Slack (Ch. 5 HITL), with the agent's evidence attached so approval takes seconds, not investigation.

Exception path: pre-approved runbooks (e.g., clear a cache) may auto-run for SEV-4/5 only.

📜 Every step on the record

Full agent traces (Ch. 5, 11) + invocation logs (Ch. 9): what it queried, what it concluded, who approved, what ran. The incident timeline writes itself — auditors and postmortems both eat for free.

Bonus: the trace IS the draft postmortem (13.4).

🛑 Loop brakes

Max 12 tool calls per incident, 5-minute reasoning budget, token cap (Ch. 5, 10). If the agent can't converge, it posts what it found and escalates — a fast, evidence-rich handoff is still a win.

Alarm: budget-hit rate > 20% means your tools or KB need work.

🧯 The agent is not the SRE

SEV-1s page humans immediately, always — the agent works alongside, pre-assembling evidence. Never gate a Tier-1 page on an LLM's judgment.

Design rule: the agent accelerates response; it never delays it.
13.6 · Your build

The capstone checklist

Build it in your own account against a toy "portal" (a Lambda API that you can break on purpose) — the pattern transfers unchanged to the real thing:

  1. Fake the portal, real the telemetry. Deploy 2–3 Lambda APIs ("claims", "benefits", "providers") behind API Gateway with logging + X-Ray on. Add a feature flag that injects failures (timeouts, 500s, dependency errors).
  2. Seed the knowledge base. Write 8–10 fake postmortems/resolution notes (vary the failure modes) into S3; create the Bedrock KB with hierarchical chunking and service-name metadata (Ch. 4).
  3. Build the read-only tools. Lambda tools wrapping Logs Insights queries, API-metrics lookups, and Athena clickstream queries — typed schemas, read-only roles (Ch. 5, 9).
  4. Assemble the agent. Strands or Bedrock Agent: instructions ("investigate, cite evidence, propose remediation, never act without approval"), tools attached, guardrail with PII masking on (Ch. 5, 6).
  5. Wire the intake and write-back. EventBridge rule (simulate ServiceNow with a custom event) → agent → update_incident writes findings to a DynamoDB "ticket" (Ch. 8).
  6. Add one remediation with approval. An SSM Automation document that flips the failure flag off ("rollback"), gated by an SNS/Slack approval step (Ch. 5).
  7. Break it and watch. Enable the failure flag, fire the incident event, and follow the agent trace end to end. Then run the 13.3 scenario yourself.
  8. Close the loop and measure. Agent drafts the resolution note → you approve → KB sync → break it again and watch it find its own past fix. Track MTTR with vs. without (Ch. 11).

🧪 Going further

1. Multi-agent split (Ch. 5): a supervisor routes to specialists — log analyst, transaction analyst, remediation operator — when the single agent's toolbox grows past ~10 tools.

2. Wire a real incident source: ServiceNow and PagerDuty both integrate with EventBridge as partner event sources.

3. Add proactive mode: CloudWatch anomaly detection fires the agent before members complain — same architecture, earlier trigger.

🎯 Chapter 13 takeaways

  1. AIOps is the course pointed inward: agent (Ch. 5) + RAG over past resolutions (Ch. 4) + guardrails (Ch. 6) operating the systems you migrated.
  2. Four evidence sources, one pattern: logs, transactions, clickstream, and change history — each a read-only tool with a typed schema.
  3. The knowledge loop is the compounding asset: every resolution becomes retrievable; seed it with existing postmortems on day one.
  4. Healthcare-grade safety: PHI masked at the tool boundary, read-only by default, human approval for anything that touches prod, full traces always.
  5. The agent accelerates response, never gates it — SEV-1s page humans exactly as before, just with the evidence already assembled.
  6. Prove it with numbers: baseline MTTR first, replay past incidents as your golden set, track auto-enrichment and wrong-hypothesis rates.
