AWS Generative AI · Chapter 2

Amazon Bedrock Deep Dive: Models & Inference

In Chapter 1 you saw where Bedrock sits. Now we go inside: how foundation models think in tokens, how your code talks to them, and how to choose the right model at the right price.

2.1 · The currency of GenAI

Tokens: how models read, write — and bill you

Foundation models don't see words or sentences. They see tokens — small chunks of text, roughly ¾ of a word each in English. Every request you send is measured in tokens in, every response in tokens out. Tokens determine three things at once: cost, latency, and how much the model can "hold in mind."

Watch a sentence become tokens:

"Migrate our helpdesk app to AWS" → 8 tokens. A 500-page policy manual? Around 250,000 tokens.

The context window is the model's working memory — the maximum tokens (prompt + response) it can handle in one exchange. Modern Bedrock models range from ~8K to over 1M tokens. On-prem analogy: it's RAM, not disk. The model "forgets" everything between calls unless you resend it.

2.3 · Talking to models

The inference APIs: Converse, InvokeModel & streaming

Your application talks to Bedrock exactly like any other AWS service: an HTTPS API, the AWS SDK, and IAM credentials. No sockets to GPUs, no model servers to patch.

Request goes in as one call; the response can stream back token by token — that's why AI chat interfaces "type."

The three calls you'll actually use

  • ConverseThe modern, model-agnostic chat API. Same request shape for every model — swap Claude for Nova by changing one string. Use this by default.
  • ConverseStreamSame as Converse, but the response arrives incrementally. Essential for chat UX: users see the first words in ~1 second instead of waiting 20.
  • InvokeModelThe lower-level API using each model's native JSON format. Needed for embeddings, image generation, and model-specific features.
# Python: one conversation, any model — just change model_id
import boto3

bedrock = boto3.client("bedrock-runtime", region_name="us-east-1")

response = bedrock.converse(
    modelId="amazon.nova-lite-v1:0",          # ← swap models here
    messages=[{
        "role": "user",
        "content": [{"text": "Summarize this incident ticket: ..."}]
    }],
    inferenceConfig={"maxTokens": 500, "temperature": 0.2}
)

print(response["output"]["message"]["content"][0]["text"])
Migration lens: to your architecture, a Bedrock call is just another downstream HTTPS dependency — like calling a payment gateway. Same patterns apply: timeouts, retries with exponential backoff, and least-privilege IAM (bedrock:InvokeModel on specific model ARNs).
2.4 · The control knobs

Inference parameters: tuning creativity vs. consistency

Models pick each next token from a probability distribution. Inference parameters reshape that distribution. One picture explains 90% of it:

"restart"
"reboot"
"cycle"
"bounce"
"unicorn"

Next-token probabilities for "First, ___ the server." Low temperature concentrates probability on the safest token; high temperature flattens the curve so unlikely tokens get picked sometimes.

  • temperature0 = deterministic and repeatable; 1 = varied and creative. Use ≤0.3 for support, summaries, and anything factual.
  • topPOnly sample from tokens covering the top P% of probability. An alternative dial to temperature — tune one, not both.
  • topKOnly consider the K most likely tokens (model-specific).
  • maxTokensHard cap on response length — your primary cost and latency guard.
  • stopSequencesStrings that halt generation, e.g. stop at </answer>.
Ops takeaway: treat parameters as configuration, not code. Store them in AWS AppConfig or Parameter Store so you can tune model behavior in production without a redeploy.
2.5 · Paying for inference

Three ways to buy: on-demand, provisioned, batch

Bedrock has no servers to reserve — you buy token throughput. Three purchasing models cover almost every workload. (Cross-region inference, next, stretches capacity further.)

On-Demand

Pay per token

No commitment; billed per 1,000 input/output tokens. The default for almost everything — like Lambda pricing, but for intelligence.

Provisioned Throughput

Reserved capacity

Buy guaranteed model units by the hour or with 1–6 month terms. For sustained, high-volume, latency-sensitive workloads — like Reserved Instances.

Batch Inference

~50% cheaper, async

Drop a file of prompts in S3, get results back later at roughly half price. Perfect for nightly jobs: summarize every ticket, classify every document.

Rule of thumb: start on-demand → move steady 24/7 traffic to provisioned → push everything that isn't interactive to batch. Nightly document processing on on-demand pricing is the classic money leak.
2.6 · Built-in resilience

Cross-region inference: capacity without the pager duty

GPU capacity is the scarcest resource in the cloud. With inference profiles, Bedrock automatically routes your requests across a set of regions — you get higher burst capacity and resilience with a one-line change (use the inference-profile ID as your modelId).

When the primary region is saturated, requests overflow to a secondary region — no code, no failover runbook.

On-prem analogy: this is your global load balancer + DR site — except AWS operates it, and "capacity planning" becomes choosing a geography (US, EU, APAC profiles keep data in-boundary).
2.7 · Trust, from day one

What happens to your data?

The first question every security team asks. The Bedrock answers are refreshingly clean:

🔒 Your prompts aren't training data

Bedrock does not use your inputs or outputs to train models, and doesn't share them with model providers. Your data stays your data.

🔑 IAM & encryption, as usual

Access controlled by IAM policies; data encrypted in transit (TLS) and at rest (KMS). Same governance muscle you use for S3 and RDS.

🕸️ Private connectivity

VPC endpoints (PrivateLink) keep traffic off the public internet — critical for migrated workloads with strict egress rules.

📋 Audit trail built in

CloudTrail records every API call; optional model invocation logging captures full prompts and responses to S3/CloudWatch for compliance.

🎯 Chapter 2 takeaways

  1. Tokens are the unit of cost, latency, and memory. The context window is RAM, not disk — stateless between calls.
  2. Learn model families, not versions: Nova (price-performance), Claude (reasoning), Llama/Mistral (open), Titan (embeddings).
  3. Use the Converse API by default — one request shape, any model, one-string model swaps. Stream for chat UX.
  4. Temperature shapes the next-token probability curve: low = consistent, high = creative. Treat parameters as config, not code.
  5. Buy inference three ways: on-demand (default), provisioned (steady high volume), batch (~50% off async work) — plus cross-region inference for burst capacity.
  6. Security fundamentals hold: prompts aren't used for training, IAM + KMS + PrivateLink + CloudTrail all apply.
