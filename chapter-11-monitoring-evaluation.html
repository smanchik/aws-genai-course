Monitoring, Evaluation & Troubleshooting: Trust but Verify

A GenAI app can be up, fast, error-free — and wrong. This chapter adds the missing discipline: measuring quality like you've always measured availability, and debugging failures that don't throw exceptions.

11.1 · The new golden signals

200 OK is not "correct"

Your classic golden signals (latency, traffic, errors, saturation) still apply — but they all read green while the model confidently tells users the wrong VPN policy. GenAI adds a fifth signal: quality. Here's the dashboard shape to aim for:

Migration lens: you've done this before. When you moved apps to AWS you added synthetic checks because "the server is up" stopped meaning "the app works." Same move again: add quality probes because "the API returned 200" doesn't mean "the answer was right."

🧰 Amazon Bedrock Evaluations

The managed version: run automatic metrics, LLM-as-a-judge, or human evaluation jobs over your dataset — including RAG evaluation that scores retrieval and generation separately.

Use for: comparing models (Ch. 2 right-sizing!), regression-testing prompt changes.

🎯 Evaluate retrieval separately

If the right chunks never arrived, the best model can't answer. Score retrieval (did the gold chunk rank top-K?) before scoring generation — it localizes the bug (Ch. 4).

Metric names: recall@K, precision@K, MRR — your search team already knows them.

🚪 Quality gates in CI/CD

From Ch. 8: golden set runs on every prompt/model/chunking change; promotion blocked below threshold. Treat a 3-point groundedness drop like a failing unit test.

Keep the set alive: add every production failure as a new test case.
11.3 · Online evaluation

Production is the real test set

👍 Feedback capture

Thumbs up/down plus an optional "what was wrong?" — the cheapest quality signal you'll ever get. Store it keyed to the invocation log entry (Ch. 9) so every complaint is replayable.

🧪 A/B & canary for prompts

Route 5% of traffic to the new prompt/model version; compare feedback rate, groundedness sample, tokens, and latency before full rollout — deployment discipline you already run, applied to prompts.

📉 Drift detection

Three things drift: user questions (new topics your KB lacks), documents (stale content), and models (provider updates). Watch "I don't know" rates and no-hit retrievals weekly.

🕵️ Sampled deep review

An LLM judge scores a few percent of live traffic asynchronously (cheap batch job — Ch. 10); humans review the worst-scored conversations weekly. That's your quality flywheel.

The loop that makes teams good: production failure → replay from invocation logs → diagnose (next section) → fix → add to golden set → gate future releases. After six months, your golden set is your moat.

📜 Invocation logs (Ch. 9)

The replay record: full prompts and responses in S3/CloudWatch. Every investigation starts here — turn it on before you need it.

🔗 X-Ray traces (Ch. 8)

One timeline across API Gateway → Lambda → KB retrieval → Bedrock → tools. Shows where the 12 seconds went and which agent step looped.

🤖 Agent traces (Ch. 5)

Bedrock agent trace / AgentCore observability: every Think→Act→Observe step with tool inputs and outputs. Non-negotiable for anything autonomous.

11.6 · Field guide

Observability failures → quick fixes

Only infrastructure metrics — "the dashboards were all green"
Add the quality tile: sampled groundedness + feedback rate + schema validity

Golden set in CI/CD + weekly sampled judging — quality is a time series, not a milestone

🎯 Chapter 11 takeaways

  1. Quality is the fifth golden signal — a GenAI app can be up, fast, and wrong. Instrument correctness like you instrument availability.
  2. Offline: golden test sets + LLM-as-a-judge (Bedrock Evaluations), with retrieval scored separately from generation.
  3. Online: feedback capture tied to invocation logs, A/B canaries for prompts, drift watching, and sampled deep review.
  4. The flywheel: failure → replay → diagnose → fix → add to the golden set → gate releases.
  5. Triage by symptom: wrong answers → retrieval first; ignored documents → grounding prompt + checks; broken JSON → schema validation + repair retry.
  6. All of it assembles from what you already built: invocation logs (Ch. 9), X-Ray (Ch. 8), agent traces (Ch. 5), custom CloudWatch metrics.
