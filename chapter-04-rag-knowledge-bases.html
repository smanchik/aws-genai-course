AWS Generative AI · Chapter 4

RAG & Knowledge Bases: Chat with Your Data

Foundation models know the internet — they don't know your runbooks, contracts, or wiki. Retrieval-Augmented Generation fixes that without training anything. This is the #1 GenAI pattern you'll build after migrating to AWS.

4.1 · The problem

Smart model, amnesiac employee

A foundation model is like a brilliant new hire on day one: deeply knowledgeable in general, but it has never seen your VPN policy, your outage runbook, or your pricing sheet — and its knowledge stops at its training cutoff. Ask anyway, and it may hallucinate: answer confidently and wrongly. Toggle below to see the difference RAG makes.

💬 "What's our policy for granting contractors VPN access?"
Why not just fine-tune? Training a model on your documents is slow, expensive, hard to update ("un-teaching" a stale policy is nearly impossible), and can't do per-user permissions. RAG keeps knowledge in a database you already know how to operate: update a document, and the next answer reflects it — like editing a config file instead of recompiling the kernel.
4.2 · The enabling trick

Embeddings: a map where meaning is distance

An embedding model (like Amazon Titan Embeddings, Chapter 2) converts any text into a vector — a point in a high-dimensional space — where texts with similar meaning land close together, even if they share no keywords. That's the trick that lets a search for "laptop won't turn on" find a document titled "notebook power failure remediation."

Try it: pick a user question. Watch it land in the space and connect to its nearest neighbors — the chunks a RAG system would retrieve. Notice: no keyword overlap needed.

On-prem analogy: like full-text search upgraded from grep to a librarian who understands what you mean.

4.3 · The architecture

The RAG pipeline: two loops, one vector store

Every RAG system — hand-built or managed — is the same two data flows. The ingestion loop (purple) runs when documents change; the query loop (blue in, teal out) runs on every user question.

The model never "learns" your data — it reads relevant excerpts at question time, like an open-book exam.

4.4 · The detail that makes or breaks RAG

Chunking: how you slice the documents

Whole documents are too big to embed meaningfully; single sentences lose context. You must split ("chunk") documents — and the strategy you choose is the most common root cause of bad RAG answers. Compare the strategies on a sample runbook:

Rules of thumb: start with the default (~300 token chunks, 10–20% overlap); use semantic or hierarchical chunking for structured docs (runbooks, policies, contracts); and always keep overlap so answers spanning a boundary aren't cut in half. Bedrock Knowledge Bases supports all three natively — plus custom chunking via Lambda.
4.5 · Where vectors live

Choosing a vector store on AWS

From Chapter 1's data layer — now with selection guidance. All of these plug into Bedrock Knowledge Bases.

🧭 OpenSearch Serverless

The default choice

Purpose-built vector engine, scales automatically, supports hybrid (keyword + vector) search. What Knowledge Bases provisions if you click "quick create."

Pick when: you have no strong reason to pick anything else.

🐘 Aurora PostgreSQL + pgvector

Vectors in your RDBMS

Add a vector column next to your relational data. One database, one backup story, familiar SQL.

Pick when: you're already migrating a PostgreSQL app — join vectors with business data.

🪣 S3 Vectors

Cheapest at scale

Vector storage directly in S3 — dramatically lower cost for large, less latency-sensitive collections.

Pick when: huge archives, batch analytics, or budget-driven designs.

🔎 Amazon Kendra

Managed retriever

Enterprise search with 40+ data connectors and built-in relevance tuning — skip embedding management entirely.

Pick when: your data lives in SharePoint/Confluence/Salesforce and you want connectors, not pipelines.

⚡ MemoryDB & Neptune

Specialists

MemoryDB for single-digit-millisecond vector lookups; Neptune Analytics for GraphRAG — combining knowledge graphs with vectors.

Pick when: extreme latency needs, or relationship-heavy questions ("who approved what?").
4.6 · The managed path

Bedrock Knowledge Bases: RAG without the plumbing

Everything in section 4.3 — chunking, embedding, vector storage, retrieval, prompt augmentation, citations — as one managed service. Point it at S3 (or Confluence, SharePoint, Salesforce…), pick an embedding model, and query it with two APIs:

  • Retrieve

    Just the search

    Returns the top-K matching chunks with scores and source URIs. You build the prompt yourself — maximum control.

  • RetrieveAndGenerate

    The whole loop

    Retrieves, augments, calls the model, and returns a grounded answer with citations. One API call for the entire RAG pattern.

# Full RAG in one call — retrieval, grounding, citations included
agent = boto3.client("bedrock-agent-runtime", region_name="us-east-1")

resp = agent.retrieve_and_generate(
    input={"text": "What's our policy for contractor VPN access?"},
    retrieveAndGenerateConfiguration={
        "type": "KNOWLEDGE_BASE",
        "knowledgeBaseConfiguration": {
            "knowledgeBaseId": "KB123EXAMPLE",
            "modelArn": "arn:aws:bedrock:us-east-1::foundation-model/amazon.nova-lite-v1:0"
        }
    }
)
print(resp["output"]["text"])          # grounded answer
print(resp["citations"])                # which chunks, from which documents
Migration lens: the ingestion loop is just an ETL job — S3 events trigger re-sync when documents change, exactly like your old file-share indexer. Citations matter operationally: they turn "trust me" into "see section 4.2 of the security policy," which is what gets security and audit teams to sign off.
4.7 · Making retrieval good

Retrieval quality: the 20% that takes 80% of the effort

🔀 Hybrid search

Combine keyword and vector search. Vectors catch meaning; keywords catch exact terms like error codes, SKUs, and hostnames that embeddings blur.

🏷️ Metadata filtering

Tag chunks (department, date, doc-type) and filter before searching: "only HR policies, only current versions." Also your permission boundary.

🥇 Reranking

A second, smarter model re-orders the top-50 hits so the truly best 5 reach the prompt. Bedrock offers managed reranker models.

Answers cite the right doc but miss the point
Chunks too small — increase size/overlap, or use hierarchical chunking
Model answers from general knowledge, ignoring your docs
Tighten the prompt: "Answer ONLY from the excerpts; otherwise say you don't know"
Exact terms (error codes, part numbers) aren't found
Enable hybrid search — pure vector search blurs identifiers
Stale answers after documents are updated
Automate sync: S3 event → Knowledge Base ingestion job, not manual refresh
Users see answers from documents they shouldn't access
Metadata filters per user/group at query time — retrieval is your ACL enforcement point

1. Upload 3–5 internal-style documents (runbooks, FAQs) to an S3 bucket and create a Bedrock Knowledge Base with the quick-create OpenSearch Serverless option.

2. In the console's Test panel, ask questions with and without "retrieval only" mode — inspect which chunks return, then re-sync after editing a document.

3. Call RetrieveAndGenerate from Python (code above) and print the citations.

🎯 Chapter 4 takeaways

  1. Models don't know your data; RAG fixes that at question time — an open-book exam, not retraining.
  2. Embeddings turn text into points where similar meaning = nearby. That's why "laptop won't turn on" finds "notebook power failure."
  3. Every RAG system is two loops: ingestion (chunk → embed → store) and query (retrieve → augment → generate).
  4. Chunking strategy is the #1 root cause of bad answers — start ~300 tokens with overlap, tune from there.
  5. Vector store choice: OpenSearch Serverless by default, pgvector if you're already on PostgreSQL, S3 Vectors for cheap scale, Kendra for connector-heavy estates.
  6. Bedrock Knowledge Bases manages the whole pipeline; RetrieveAndGenerate gives grounded, cited answers in one call.
  7. Quality levers: hybrid search, metadata filtering (also your ACLs), and reranking.
