AWS Generative AI · Chapter 3

Prompt Engineering that Actually Works

The prompt is your new configuration file. In this chapter you'll learn the anatomy of a production-grade prompt, the five techniques that cover 95% of real work, and how AWS helps you version, test, and govern prompts like any other artifact.

3.1 · The mindset shift

You're not chatting — you're writing a spec

In Chapter 2 you saw that models predict tokens based on the input you give them. That makes the prompt the single highest-leverage engineering surface in a GenAI app: the same model can be useless or excellent depending entirely on what you send it. Think of a prompt the way you think of a work order for a contractor — a very capable one who takes everything literally and knows nothing about your company unless you tell them.

Migration lens: prompts are configuration, not conversation. They belong in source control, they need code review, they need testing, and they will need rollbacks. Everything you know about managing httpd.conf applies — except this config file is written in English.
3.2 · Anatomy of a prompt

The six building blocks

Production prompts aren't one sentence. They're structured documents with up to six parts. Hover or tap each block to see what it does — this example turns a model into a ticket-triage assistant for a migrated helpdesk app.

1 · Role You are a senior IT support triage specialist for AnyCompany's internal helpdesk.
2 · Context AnyCompany has 4 support tiers. Hardware issues go to Tier 1, access/password to Tier 2, application errors to Tier 3, security incidents to Tier 4 (urgent).
3 · Task Classify the ticket below into exactly one tier and write a one-sentence justification.
4 · Examples Ticket: "Laptop screen flickers" → {"tier": 1, "reason": "Physical hardware fault."}
Ticket: "Can't log into VPN" → {"tier": 2, "reason": "Access/credential issue."}
5 · Output format Respond with JSON only: {"tier": <1-4>, "reason": "<one sentence>"}. No other text.
6 · Input data Ticket: "Strange outbound traffic from the finance file server since 02:00."
  • RoleSets persona and domain. Dramatically shapes tone and vocabulary.
  • ContextThe business knowledge the model can't know. Your rules, your data.
  • TaskOne clear instruction. Ambiguity here is the #1 cause of bad outputs.
  • Examples (few-shot)Show, don't tell. 2–5 examples often beat a page of instructions.
  • Output formatMake responses machine-parseable — your code consumes this, not a human.
  • Input dataThe variable part — injected by your application at runtime.

Blocks 1–5 form your template (static, versioned); block 6 is runtime data your app injects.

3.4 · The technique toolbox

Five techniques cover 95% of production work

🎯 Zero-shot

Just ask

A clear instruction with no examples. Modern models handle simple, common tasks this way — summarize, translate, extract.

Use when: the task is unambiguous and generic. Cheapest in tokens.

📋 Few-shot

Show 2–5 examples

Demonstrate the pattern with solved examples. The single most reliable quality upgrade — especially for classification and formatting.

Use when: output must follow your conventions (codes, tiers, styles).

🪜 Chain-of-thought

"Think step by step"

Ask the model to reason before answering. Trades extra tokens for large accuracy gains on multi-step logic, math, and policy decisions.

Use when: the answer requires reasoning, not recall. See it in action below.

🧱 Structured output

JSON in, JSON out

Specify an exact schema and demand nothing else. Turns a chatty model into a dependable API your downstream code can parse.

Use when: a program — not a person — consumes the response. (Almost always.)

🔗 Prompt chaining

Decompose the job

Split complex work into sequential prompts: extract → validate → summarize. Each step is simpler, testable, and can use a cheaper model.

Use when: one mega-prompt keeps failing. Orchestrate with Step Functions or Prompt Flows.
3.5 · Chain-of-thought, animated

Why "think step by step" works

A real policy question from a migration project: "Our file server has 4 TB used, growing 1 TB/quarter. The S3 migration window is in 9 months. Will a 10 TB allocation suffice for the first year after migration?"

⚡ Direct answer (no reasoning)

!
"Yes, 10 TB should be plenty for your file server."

Sounds confident. Never did the math. Coin-flip reliability.

🪜 Chain-of-thought

1
Current usage: 4 TB. Growth: 1 TB/quarter.
2
Migration in 9 months = 3 quarters → 4 + 3 = 7 TB at cutover.
3
First year after migration = 4 more quarters → 7 + 4 = 11 TB.
4
11 TB > 10 TB allocation.
✓
No — allocation falls ~1 TB short in month 9 post-migration.

Auditable reasoning you can verify — and catch when it's wrong.

Bonus: newer models (Claude, Nova Premier) have built-in "extended thinking" modes that do this internally. You still benefit from requesting visible reasoning when you need an audit trail — e.g., for change-approval decisions.
3.6 · From prompt to template

Parameterize it: prompts as versioned artifacts

Hard-coding prompt strings inside application code is the GenAI equivalent of hard-coding database passwords. Separate the template (owned, reviewed, versioned) from the variables (injected at runtime).

# Bedrock Converse with a system prompt + templated user message
SYSTEM_PROMPT = """You are a senior IT support triage specialist for AnyCompany.
Tiers: 1=hardware, 2=access, 3=application, 4=security (urgent).
Respond with JSON only: {"tier": <1-4>, "reason": "<one sentence>"}"""

def triage(ticket_text: str):
    return bedrock.converse(
        modelId="amazon.nova-lite-v1:0",
        system=[{"text": SYSTEM_PROMPT}],                # the template
        messages=[{"role": "user",
                   "content": [{"text": f"Ticket: {ticket_text}"}]}],  # the variable
        inferenceConfig={"maxTokens": 150, "temperature": 0.1}
    )
System vs. user messages: the system field carries your standing instructions and gets stronger adherence from the model — users can't easily override it. Put blocks 1–5 there; keep only runtime data in the user message. This is also your first line of defense against prompt injection (Chapter 6 goes deeper).

3.7 · Field guide

Common failures → quick fixes

"Make this better" — vague verbs, no success criteria
"Rewrite for a non-technical audience in ≤3 sentences, keeping all version numbers"
Telling the model what not to do ("don't be verbose, don't speculate…")
State what to do: "Answer in ≤50 words. If unsure, reply exactly: UNKNOWN"
One mega-prompt doing extraction + analysis + formatting + translation
Chain small prompts; each step testable, each can use the cheapest adequate model
Assuming the model knows your acronyms, org chart, or current date
Inject context explicitly — the model only knows what's in the prompt (or the RAG pipeline, Ch. 4)
Parsing free-text answers with regex and hoping
Demand a JSON schema, validate it, and retry on parse failure
Editing prompts live in production code
Prompt Management versions + golden tests + staged rollout

🎯 Chapter 3 takeaways

  1. A prompt is a spec, not a chat — treat it like configuration: versioned, reviewed, tested, rollback-able.
  2. Production prompts have six parts: role, context, task, examples, output format, input data. The first five are your template.
  3. Five techniques cover 95% of work: zero-shot, few-shot, chain-of-thought, structured output, and prompt chaining.
  4. Chain-of-thought buys accuracy and an audit trail on reasoning tasks — for the price of extra tokens.
  5. Put standing instructions in the system message; inject runtime data in the user message.
  6. Bedrock Prompt Management gives prompts a CI/CD-style lifecycle: draft → test → version → deploy → monitor.
