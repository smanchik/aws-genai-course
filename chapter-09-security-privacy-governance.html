9.2 · Identity is the perimeter

IAM for AI: scope by model, gate by team

Every Bedrock call is an authenticated, authorized AWS API call — which means your entire IAM toolbox applies. Three levels matter:

# Level 1 — Workload policy: THIS app may invoke ONE model (and nothing else)
{ "Effect": "Allow",
  "Action": ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream"],
  "Resource": "arn:aws:bedrock:us-east-1::foundation-model/amazon.nova-lite-v1:0" }
#              never "Resource": "*" — that grants every model, including the expensive ones

# Level 2 — Guardrail enforcement: deny invocations that DON'T carry the guardrail
{ "Effect": "Deny",
  "Action": "bedrock:InvokeModel", "Resource": "*",
  "Condition": { "StringNotEquals": {
      "bedrock:GuardrailIdentifier": "arn:aws:bedrock:us-east-1:111122223333:guardrail/gr-corp" }}}

# Level 3 — Organizations SCP: the whole org may only use approved regions
{ "Effect": "Deny", "Action": "bedrock:*", "Resource": "*",
  "Condition": { "StringNotEquals": { "aws:RequestedRegion": ["us-east-1", "eu-central-1"] }}}
Level 2 is the underrated one: an IAM condition that makes guardrails mandatory, not optional. No developer can "temporarily" ship without the policy layer — the platform enforces it, like a mandatory proxy in your old data center.
9.3 · Private by default

VPC endpoints: prompts that never touch the internet

By default, Bedrock's API endpoint is public (TLS-protected, but public). For regulated workloads — or just strict egress rules carried over from on-prem — use AWS PrivateLink: an interface VPC endpoint keeps every prompt and response on the AWS network.

Teal = private path via PrivateLink. Red = the path that no longer exists. The endpoint policy adds another gate: only listed roles may call only listed models through this endpoint.

Migration lens: this is your old "no direct internet from the app tier" rule, preserved in the cloud. Combine with security groups and you can prove to auditors that AI traffic never left your controlled network path — same evidence pattern as your database tier.
9.4 · Data protection

Keys, residency, retention: the privacy trio

🔑 Encryption & KMS

In transit: TLS everywhere. At rest: knowledge bases, agent sessions, guardrail configs, and logs all support customer-managed KMS keys — your keys, your revocation power, CloudTrail on every decrypt.

Do: CMKs for anything touching regulated data; key policy ≠ IAM policy — set both.

🌍 Residency & cross-region

Bedrock processes data in the region you call — until you enable cross-region inference (Ch. 2), which routes within a defined geography (US, EU, APAC profiles).

Do: for GDPR-scoped data, pick EU profiles and pin regions with the SCP from 9.2.

🗓️ Retention & minimization

The model keeps nothing between calls — but your DynamoDB history, invocation logs, and vector stores do. That's where privacy regulation actually lands.

Do: TTL on conversation tables, lifecycle policies on log buckets, Macie scans on document buckets feeding knowledge bases.

🧹 The deletion question

"Delete user X's data" (GDPR Art. 17) means: their conversation history, their documents in the KB and its vectors after re-sync, and log entries per your retention policy.

Do: design the deletion runbook before launch — retrofitting it is painful.
Repeat the Chapter 2 promise, because auditors ask: Amazon Bedrock does not use your prompts or completions to train models, and does not share them with model providers. Your exposure lives in your own stores — history tables, logs, vector indexes — which is exactly where your existing data governance applies.
9.5 · Audit & observability

Interactive: which log answers which question?

Three log streams, three different jobs. Pick an auditor's question and see which source lights up — knowing this mapping cold is half of every compliance review:

🗂️ AWS CloudTrail Every management API call: who, what, when, from where. The control-plane record.
📜 Bedrock Model Invocation Logs Opt-in capture of full request/response bodies (prompts, completions, token counts) to S3/CloudWatch.
📈 CloudWatch Metrics & X-Ray Invocation counts, token metrics, latency percentiles, error rates, traces across services.
Turn invocation logging on early — it's opt-in, and the incident you'll want it for won't announce itself in advance. Encrypt the log bucket with a CMK, lifecycle it per policy, and restrict read access: prompt logs are themselves sensitive data.
9.6 · Scaling control

Governance: from one AI app to fifty

The first GenAI app is a project; the tenth is a platform. Borrow the multi-account discipline from your migration landing zone:

  1. Model allow-list via SCP & model access. Approve model families centrally (legal reviews licensing once); deny the rest org-wide. New model requests follow the same path as new SaaS vendors.
  2. A GenAI gateway account. Central account owning guardrails, invocation logging, and cost allocation; app accounts call through it. One place to audit, one place to tune (the "gateway architecture" from the Bedrock ecosystem).
  3. AI inventory in your CMDB. Every assistant/agent registered: owner, model, guardrail version, data sources, risk tier. If it's not inventoried, it's shadow AI.
  4. Risk-tiered review. Internal FAQ bot ≠ customer-facing advisor ≠ agent with write access. Define 3 tiers with proportionate review — don't CAB-review a lunch-menu bot.
  5. Compliance evidence on tap. AWS Artifact for AWS-side attestations; AWS Config rules for your-side drift (unencrypted buckets, endpoints removed); Audit Manager to assemble the evidence package.
  6. An AI usage policy people can read. One page: approved tools, banned inputs (customer PII into consumer chatbots), escalation path. The Q Business rollout from Chapter 7 is your carrot — a safe tool beats a banned one.
9.7 · Field guide

Security failures → quick fixes

bedrock:* on Resource: * because permissions were "blocking the sprint"
Model-scoped ARNs per workload; a broad policy is a one-line change away from an expensive surprise
Guardrails optional, relying on developers to remember
IAM condition denying un-guardrailed invocations (9.2 Level 2) — enforced, not encouraged
Invocation logging "later" — it's launch week
Logging on from day one; you can't investigate what you didn't record
Prompt logs readable by every developer
Logs are sensitive data: CMK-encrypted, least-privilege read, lifecycle-expired
Conversation history kept forever "for future fine-tuning"
TTL by policy now; a hypothetical future use case doesn't justify indefinite PII retention
Each team wiring its own Bedrock setup, differently
Gateway account + landing-zone blueprints — the same fix as your migration's account sprawl

🧪 Hands-on lab (~60 min)

1. Rewrite your Chapter 8 Lambda role to the model-scoped policy from 9.2 — verify a call to any other model fails with AccessDenied.

2. Add the guardrail-enforcement deny condition and confirm an un-guardrailed invoke is rejected.

3. Create an interface VPC endpoint for bedrock-runtime, run your app in a private subnet, and confirm calls succeed with no internet route.

4. Enable model invocation logging to a CMK-encrypted bucket; find your own test prompt in the logs, then answer all five questions from section 9.5 using the right source.

5. Deeper: Bedrock security docs · Bedrock + PrivateLink · GenAI Lens: security pillar.

🎯 Chapter 9 takeaways

  1. Shared responsibility, GenAI edition: AWS secures the model service; you secure prompts, data, identities, and networks — same split you learned in migration.
  2. IAM in three levels: model-scoped ARNs per workload, a deny condition making guardrails mandatory, and SCPs pinning approved models/regions org-wide.
  3. PrivateLink endpoints keep prompts off the internet — your old "no direct egress from the app tier" rule, preserved.
  4. Privacy lives in your stores: KMS CMKs, region pinning for residency, TTL/lifecycle retention, and a deletion runbook designed before launch.
  5. Know the log map cold: CloudTrail = who changed what, invocation logs = what was said, CloudWatch/X-Ray = how it's performing. Turn invocation logging on early.
  6. Scale governance like your landing zone: model allow-lists, a gateway account, AI inventory in the CMDB, risk-tiered reviews.
