AWS Generative AI · Chapter 5

Agents & Agentic AI: From Answering to Acting

RAG made the model informed. Agents make it useful — able to look things up, call your APIs, and finish multi-step tasks. This chapter shows how agents work, the AWS ways to build them, and the guardrails that keep them on a leash.

5.1 · The leap

A chatbot tells you. An agent does it.

Everything so far has been one question → one answer. An agent wraps the model in a loop and hands it tools — functions it may call. Given a goal, it plans steps, executes them, checks results, and keeps going until the job is done. Same ticket, two experiences:

💬 Chatbot (Chapters 2–4)

"Extend contractor J. Rivera's VPN access by 30 days."
"To extend contractor VPN access, you need sponsor approval per SEC-VPN-007. Submit form AC-31 in the Access Portal, then IT will…"
…and now a human does five manual steps.

🤖 Agent (this chapter)

"Extend contractor J. Rivera's VPN access by 30 days."
🔍 looked up user📋 checked policy ✉️ requested sponsor approval🔑 scheduled extension
"Done. Sponsor approved at 14:02; access extended to Oct 14 and logged as change CHG-4482."
On-prem analogy: a chatbot is a knowledge-base article; an agent is the runbook plus the engineer executing it. The formula to remember: Agent = Model (reasoning) + Tools (your APIs) + Loop (keep going) + Memory (context across steps).
5.2 · The engine

The agent loop: Think → Act → Observe

Under the hood, almost every agent runs the same cycle (the research name is ReAct — Reason + Act). The model never executes anything itself — it requests a tool call; your code executes it and feeds the result back.

The orange dot is one task cycling the loop. Each lap = one model call + one tool call. More laps = more capability — and more tokens, latency, and risk. That tradeoff is agent engineering.

5.4 · The mechanics

Tool use (function calling): the contract

You describe each tool to the model — name, purpose, JSON parameter schema. When the model wants to use one, it responds not with prose but with a structured toolUse request. The Converse API makes this a first-class citizen:

# 1. Describe the tool (the contract)
tools = [{"toolSpec": {
    "name": "extend_vpn",
    "description": "Extend a contractor's VPN access. Requires prior sponsor approval.",
    "inputSchema": {"json": {
        "type": "object",
        "properties": {"username": {"type": "string"},
                       "days": {"type": "integer", "maximum": 30}},
        "required": ["username", "days"]}}}}]

# 2. The model responds with a request — not an action
resp = bedrock.converse(modelId=MODEL, messages=msgs, toolConfig={"tools": tools})
# → {"toolUse": {"name": "extend_vpn", "input": {"username": "jrivera", "days": 30}}}

# 3. YOUR code validates and executes, then returns the result to the model
result = extend_vpn(**tool_input)          # ← IAM permissions live HERE, not in the model
msgs.append(tool_result_message(result))   # loop continues…
The security line that matters: the model suggests; your code executes. Validate every argument (that maximum: 30 is doing real work), and scope the executing role's IAM permissions to exactly what the tool needs. The agent's power is your Lambda's IAM policy — nothing more.
5.5 · The standard

MCP: a USB-C port for tools

Writing bespoke tool integrations for every agent doesn't scale. The Model Context Protocol (MCP) is an open standard: wrap a system once as an MCP server, and any MCP-aware agent can use it — same idea as USB-C replacing a drawer of proprietary cables.

Build the CMDB integration once; every agent in the company can use it. Note the last server — MCP is also how agents reach systems still on-prem mid-migration.

5.6 · Building on AWS

Three ways to build agents (and when to mix them)

🧩 Strands Agents

Code-first · open source

AWS's open-source Python SDK: define an agent in a few lines — model + tools + prompt. MCP-native, works with Bedrock or any model. You own the loop.

Pick when: developers want full control and testability — the "write the runbook yourself" path.

🛠️ Amazon Bedrock Agents

Managed & console-driven

Define instructions, attach action groups (Lambda/OpenAPI) and Knowledge Bases; AWS runs the loop, memory, and orchestration. Built-in trace view for debugging.

Pick when: you want the fastest managed path with the least code.

🏗️ Bedrock AgentCore

Production infrastructure

Framework-agnostic runtime for any agent (Strands, LangGraph, CrewAI…): secure serverless execution, session isolation, memory, identity, gateway to tools, and observability.

Pick when: moving agents from laptop demos to production — it's the "EKS for agents."

👥 Multi-agent patterns

Divide and conquer

A supervisor agent routes work to specialists (billing agent, network agent, security agent). Bedrock supports supervisor/collaborator natively; Strands composes agents as tools.

Pick when: one agent's toolbox gets too big — same reason you split a monolith.

⚙️ Step Functions orchestration

Deterministic backbone

For workflows that are mostly fixed with a few AI decisions, keep Step Functions in charge and call Bedrock at the branching points. Predictable, auditable, cheap.

Pick when: the process is regulated or well-known — don't buy a loop you don't need.
Decision shortcut: known process, few decisions → Step Functions + Bedrock. Open-ended tasks, developer team → Strands on AgentCore. Fast managed start → Bedrock Agents. These compose: many production systems use all three.
5.7 · Keeping the leash on

Agent safety: autonomy needs brakes

An agent is automation that decides its own steps — so it gets the controls you'd give a new operator with a pager: limited permissions, supervision, and a hard stop.

🔐

Least-privilege IAM

The tool's execution role defines the blast radius. Read-only tools by default; write tools scoped to specific resources.

🛑

Stopping conditions

Max loop iterations, token budgets, and timeouts. A confused agent must fail fast, not spiral (and bill) forever.

🙋

Human-in-the-loop

Irreversible or costly actions (delete, pay, grant access) pause for approval — like change advisory board, but per-action.

🛡️

Guardrails on I/O

Bedrock Guardrails filter both user input and agent output — prompt-injection attempts included. Chapter 6 goes deep.

📜

Full tracing

Log every thought, tool call, and result (Bedrock agent traces / AgentCore observability). If you can't replay it, you can't debug or audit it.

🧪

Evaluate task completion

Test agents on scripted scenarios: task completion rate, wrong-tool calls, runaway loops — before and after every change.

One mega-agent with 40 tools "to be safe"
Few tools per agent; split into specialists when the toolbox grows past ~10
Agent's role has AdministratorAccess "for the demo"
Per-tool roles with the minimum actions on the minimum resources
Trusting tool arguments because "the model is smart"
Validate every argument against schema and business rules before executing
No iteration cap — the agent "will figure it out"
Hard limits: N loops, T seconds, $ budget; alert on hitting any of them
Shipping an agent nobody can observe
Traces on day one — every step logged, queryable, and replayable

🎯 Chapter 5 takeaways

  1. Agent = model + tools + loop + memory. A chatbot explains the runbook; an agent executes it.
  2. The engine is Think → Act → Observe (ReAct), repeating until the goal is met. Each lap costs tokens, latency, and risk.
  3. Tool use is a contract: the model requests, your code validates and executes — IAM and argument validation are the real security boundary.
  4. MCP is the USB-C of tools: wrap a system once, every agent can use it — including systems still on-prem.
  5. Three AWS paths that compose: Strands (code-first), Bedrock Agents (managed), AgentCore (production runtime) — with Step Functions when the process is mostly deterministic.
  6. Safety is non-negotiable: least-privilege IAM, stopping conditions, human approval for irreversible actions, and full traces from day one.
